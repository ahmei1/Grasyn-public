GraSyn: what we have built so far

A collaboration workspace for small software teams, where tasks, decisions, conversations, and now GitHub code live in one connected place. This report covers everything finished in Phase 1 (the core workspace), Phase 2 (live teamwork: live updates, presence, project discussions, and meeting records), and Phase 3 (task keys and GitHub: pushes and pull requests linked to tasks), on both the backend and the frontend.

Where the project stands

Phases 1, 2, and 3 are complete. A project now holds the work, the conversation about it, and the code that implements it: tasks with short keys, a live discussion, meeting records whose action items become real tasks, and GitHub pushes and pull requests linked by those keys. Everything is stored so a later AI summary can read it. Video calls and AI summaries come next.

Phase 1: core workspace Complete

Accounts, teams and roles, invitations, projects, tasks with a Kanban board, comments, task history, notifications, a dashboard, and a new landing page.

Phase 2: real-time teamwork Complete

Phase 3: GitHub Complete

Every task has a short key. Connecting a GitHub App records pushes and pull requests, links them when the key is in a branch, commit, or PR, and shows that code on the task and the project.

Features

Accounts and sessions

  • Register, sign in, sign out, and refresh the session
  • Passwords hashed with argon2
  • Short-lived access cookie (15 minutes) and a rotating refresh token, stored hashed
  • Sign-in limited to 8 attempts per minute

Workspaces and roles

  • Owner, admin, and member roles
  • Invite links that expire
  • Only the owner can invite admins
  • Owners and admins change roles and remove members

Projects

  • Create, edit, archive, restore, and delete
  • Status, priority, and start and due dates (start must come before due)
  • Project members
  • Only the creator or an admin can manage a project

Tasks

  • Four columns: To do, In progress, In review, Done
  • Priority, assignee, due date, and description
  • Safe reordering with a row lock, so two people moving cards never collide
  • Members can update only their own tasks, and only the status and description

History and notifications

  • Every change is recorded in plain words, for example "changed due date from 3 Oct to 10 Oct"
  • A separate audit trail for sensitive actions
  • Notifications with read and read-all
  • Saves that change nothing are not recorded

Dashboard

  • Real counts: open, overdue, due soon, and stale tasks
  • My tasks, recent projects, and recent activity
  • Due dates are compared in UTC, so time zones don't shift them

Project discussion Phase 2

  • Any workspace member can read and post in a project
  • Authors edit their own messages; authors and admins can delete
  • Loads 50 at a time, with older pages on request
  • New messages appear live for people with the project open, notify the project's followers, and stay out of the activity feed

Meeting records Phase 2

  • Title, start and end time, participants, notes, decisions, and action items
  • Invited people get a notification and can edit the record
  • Only the organizer, the project creator, or an admin can delete it
  • Note edits refresh open screens without filling the feed

Action items become tasks Phase 2

  • Uses the normal task rules, so members still can't set an assignee or due date
  • Each item can become a task only once, even if two people click at the same time
  • The task keeps a link back to its meeting

Task keys Phase 3

  • A short key per task, such as GS-42, from the workspace prefix and a number
  • The next number is taken inside the same save as the task, so two creates cannot share a number
  • Admins can change the prefix in workspace settings

GitHub connection Phase 3

  • Owners and admins connect the GitHub App from workspace settings
  • The redirect is tied to that workspace with a short-lived signed token
  • Each repository can be assigned to a project, which puts its code on that project's Code tab

Stored project context Phase 2

One endpoint, GET /projects/:id/context, returns a project's tasks (including each task's number), its latest 200 discussion messages, every meeting with its participants, notes, decisions, and action items, the latest 100 activity entries, and now the latest 100 pull requests and 100 commits linked to the project. Lists read oldest first, like a timeline, and each task says which meeting it came from. This is the input the AI summaries will use.

GitHub webhooks and linking Phase 3

GitHub signs every webhook with HMAC over the raw body. Each delivery id is stored, so a retry does not create the same commit twice. A push, pull request, or review is linked to a task when the workspace prefix and number appear in the branch name, commit message, or pull request title or description. Merging or reviewing a linked PR notifies the assignee. Merging does not move the task; if it is not already Done, the task page offers a "Mark as done" prompt.

Realtime layer (Phase 2)

Secure connection

The live connection uses the same sign-in cookie as the API. A missing or invalid session is disconnected right away. Joining a workspace, project, or task "room" runs the same membership checks as the API.

Only real changes are sent

Signals are queued while a save is running and sent only after it succeeds. If the database rejects the save, nothing is sent, so other screens never refresh to data that doesn't exist.

Presence

The server tracks which project or task each open tab is showing. A person with several tabs counts once, and stays online until their last tab closes.

Notifications for the right people

The assignee, the project creator, and now every workspace admin and the owner. Each person gets one notification per change, and whoever made the change gets none.

Someone saves a change→Permission check→Database save→History and notifications written→Live signal sent→Teammates' screens refresh

Who gets notified

The current rules, including the fix for admins. Whoever made the change is never notified about their own action.

EventAssigneeProject creatorWorkspace owner and adminsPerson who made the change
New task createdYes (assigned)YesYesNo
Task changed (status, priority, date, details)YesYesYesNo
Task reassignedYes (new assignee)YesYesNo
New commentYesYesYesNo
Linked pull request reviewed or mergedYesNoNo— (GitHub user)

If one person holds several of these roles, for example an admin who is also the assignee, they still get only one notification. When someone is added to a meeting, they are notified too, unless they added themselves. A new discussion message notifies the project creator, the project's members, the workspace owner and admins, anyone with a task in the project, and anyone who has posted in that discussion. Each person keeps at most one unread discussion notification per project, which updates with the latest message, and it clears when they open the Discussion tab.

What makes it feel good

Live without refreshing

When a teammate moves a task or comments, the board, task page, dashboard, and notification badge update by themselves.

See your team

The sidebar shows who is online now. Projects, boards, and tasks show the faces of anyone else on the same page.

Clear permissions

Each screen says what you are allowed to do, for example "Execution access", and hides the actions you can't take.

Steady layout

The sidebar stays in place and only the content area scrolls. Every screen has loading, empty, and error states.

Motion with care

The landing animations use GSAP and Lenis smooth scrolling. People who turn off motion in their system settings get a calm, static version.

Fast to load

The animation libraries load only on the landing page (about 68 KB compressed), so the workspace app stays light.

Talk where the work is

Each project has its own discussion. Enter sends, Shift+Enter adds a line, and new messages appear for everyone on the page.

Meetings that lead to work

Decisions and follow-ups are written down during the meeting, and a follow-up becomes a board task in one click.

Edits that don't collide

Unsaved meeting notes are kept while teammates make changes, and the app clearly marks what is not saved yet.

Code next to the task

Put the task key in a branch, commit, or pull request, and that work appears on the task and on the project's Code tab as it happens.

Known limits to keep in mind

Presence covers one server. It is kept in memory. If the app later runs on several servers, it will need a shared store such as Redis.

Google and GitHub sign-in are not built yet. The buttons are there but clearly marked as unavailable.

The link-preview image needs the real domain. Once the site is live, the preview tag must use the full address.

Notifications are in-app only. There are no email or push notifications yet.

Discussions are plain text. There are no @mentions, files, or reactions yet.

Meeting times use each person's browser time zone. There is no calendar sync or reminder yet.

Changing a task prefix stops old keys from linking. Code that still mentions OLD-12 will not match the new prefix.

Disconnecting GitHub in Grasyn does not uninstall the app on GitHub. Webhooks for that install are ignored until someone connects it again, or uninstalls it on GitHub.

Local GitHub webhooks need a relay. GitHub cannot reach localhost, so a tool such as smee.io forwards signed events to the API.
